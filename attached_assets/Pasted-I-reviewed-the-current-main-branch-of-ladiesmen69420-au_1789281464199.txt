I reviewed the current main branch of ladiesmen69420/autosender, focusing on the API server, scheduler, Discord routes, authentication, database schemas, auto-reply logic, gateway/warm-up code, and the main React UI. I did not modify anything.

I found several serious bugs. The most important ones should be fixed before adding more features:

CRITICAL — Campaign ownership bypass / IDOR. In artifacts/api-server/src/routes/campaigns.ts, most /:id operations check only campaignsTable.id === id, not userId. A user who guesses another campaign ID can potentially edit, delete, start, stop, reset, test-send, read logs, clear logs, or change rate-limit settings on someone else's campaign. duplicate is particularly dangerous because it copies the victim campaign's Discord token into the new campaign and then returns that campaign.
CRITICAL — Discord tokens can leak through null-user campaigns. userFilter() deliberately includes userId IS NULL for signed-in users. Meanwhile campaign creation does not require authentication, so anonymous campaigns can be created with userId=null. Every authenticated user can then see those shared/null campaigns. Because serializeCampaign() spreads the entire database row, the Discord token is returned too.
CRITICAL — /api/discord/sessions exposes stored Discord tokens. The sessions database table has no userId, and GET /discord/sessions returns every session including its plaintext token. POST and DELETE are also not user-scoped. This is probably the single easiest token-leak path in the repository.
HIGH — Most /api/discord/* routes have no authentication requirement. clerkMiddleware() parses authentication but does not itself protect routes. The Discord router doesn't call getAuth()/requireAuth(). This includes token validation, sending, fetching DMs, AI replies, presence, warm-up, and legacy auto-reply endpoints. The AI endpoints therefore also let unauthenticated callers consume your server-side OpenAI quota.
HIGH — AI reply campaigns have the same null-user ownership problem. Signed-in users can see and modify ai_reply_campaigns whose userId is null. Anonymous POST can create those records.
HIGH — Discord OAuth has no state validation. routes/auth.ts creates the Discord authorization URL without a random state, and the callback accepts the returned code directly. That leaves the login flow vulnerable to login-CSRF/session-confusion attacks.
HIGH — Discord OAuth email linking is too trusting. The callback links an existing Clerk account by the email returned from Discord, but doesn't retrieve/check Discord's verified status before creating a Clerk sign-in token. Account linking should be substantially stricter.
HIGH — Credentialed CORS is effectively open. app.ts uses cors({ credentials: true, origin: true }), which reflects arbitrary origins while permitting credentials. You should use an explicit production-origin allowlist.
HIGH — Discord tokens are repeatedly exposed to the browser. Campaign GET responses contain the complete token rather than a masked value. The frontend also stores campaign/token data in localStorage through useLocalState, including bb_drafts, bb_new_form, bb_token_input, bb_presence_token, and bb_warmup_token. An XSS or another user of the browser could recover them.
HIGH — Clerk sign-in ticket is put into the URL query string. OAuth redirects to /discord-signin?token=.... The page reads it but never immediately removes it from the address bar. It may remain in browser history and potentially other URL-based telemetry.
HIGH/MEDIUM — Fresh campaign page can crash. In home.tsx, const draft = getDraft(campaign.id) may initially be null, because drafts are populated later by an effect. But rendering subsequently accesses draft.rotateEnabled directly. On a fresh browser with pre-existing campaigns this can throw before the effect gets a chance to populate the draft.
MEDIUM — “Commands” and “Message” are literally the same input. In the New Campaign form, both textareas use value={newForm.message} and both update message. Typing in Commands overwrites Message and vice versa. commandsEnabled also exists in local state but doesn't have a meaningful backend implementation.
MEDIUM — Send window start === end means “never send.” The auto-reply scheduler explicitly treats equal hours as 24 hours active, but the campaign scheduler doesn't. A campaign configured as 9:00 AM → 9:00 AM will always be outside its window.
MEDIUM — Outside-window campaigns wake every 2 seconds and spam logs. executeCampaignCycle() calculates minutesUntilWindowOpen(), but then ignores it and returns nextMs: 2000. An overnight campaign can therefore create thousands of identical “Outside send window” log rows instead of sleeping until the window opens.
MEDIUM — sentToday uses server-local midnight, while scheduling uses Singapore time. getSentToday() calls setHours(0,0,0,0) on the server. If the server is UTC, the dashboard's “today” counter resets at 8 AM Singapore time rather than midnight SGT.
MEDIUM — Auto-reply scheduler can silently die after one DB exception. runScan() sets state.running=true, then performs its first DB query outside its main try block. If that query rejects, state.running stays true and the timer callback never reaches scheduleNext(). That user's auto-reply can remain dead until manually restarted.
MEDIUM — Warm-up does not actually enforce its main promise. discord-warmup.ts exports isWarmupActive(), and comments say sending is prevented while warm-up is active. Repository search shows isWarmupActive() is never actually called anywhere; it is merely imported in routes/discord.ts. So the protection isn't wired up.
MEDIUM — Warm-up state leaks memory. When a warm-up naturally expires, its entry remains in the global WARMUPS map. There is also no sensible upper limit on days. Combined with the unauthenticated warm-up endpoint, many unique tokens could produce persistent state/resource consumption.
MEDIUM — Gateway first-heartbeat timer cannot be cancelled. discord-gateway.ts schedules the initial jittered heartbeat with an untracked setTimeout. teardown() can clear the interval and watchdog but not this timeout. If the socket closes/reconnects before that timeout fires, the old timeout can later create an extra heartbeat interval against the new connection.
MEDIUM — AI model setting is inconsistent. /discord/ai-reply respects OPENAI_MODEL, and the server-side auto-reply scheduler does too, but legacy /discord/auto-reply hardcodes "gpt-5.2". Changing OPENAI_MODEL therefore doesn't change all AI calls.
LOW/MEDIUM — Campaign messageVariants appears unfinished. The database and campaign API save/copy messageVariants, but scheduler.ts always sends campaign.message. The frontend campaign type doesn't expose variants either. So that setting currently has no effect.
LOW/MEDIUM — Partial send-window updates are broken. PUT /campaigns/:id supports partial fields, but supplying only sendWindowStart or only sendWindowEnd causes validation to complain that both must be provided instead of combining the changed value with the stored counterpart.
LOW — lastSentAt is really “last attempted cycle.” Scheduler updates it even when zero messages successfully send. The UI can therefore imply a message was sent when the whole cycle failed.
LOW — Logs lack a database foreign key to campaigns. campaign_logs.campaign_id is just an integer. Normal route deletion manually clears logs, but other deletion paths/database maintenance can leave orphaned records.

There are also intentional sections aimed at making automated Discord activity appear human or bypass spam/selfbot detection. I haven't suggested ways to make those evasion mechanisms more effective; the issues above are security, data-isolation, reliability, and normal application-functionality problems.
